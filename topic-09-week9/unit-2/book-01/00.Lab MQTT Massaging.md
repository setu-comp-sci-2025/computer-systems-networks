# Lab: MQTT Messaging

### **Overview**

In the previous lab, you built a **Flask web API** on the Raspberry Pi that exposed Sense HAT data and allowed LED control via REST endpoints.
 In this lab, you’ll create a Python program that uses **MQTT**  (no Flask) that:

1. **Publishes** environment data
2. **Subscribes** to LED command messages
3. **Publishes** LED state (**retained**)
4. **Advertises** online/offline via **LWT**

Each stage adds just enough code to learn the concept, with tests you can run immediately.

## Topic Design (what we publish/subscribe to)

We’ll namespace topics by `/<userID>/...` so multiple users/devices can coexist safely on the public MQTT broker. Select a `<userID>` that is unique to you - for example I use my GitHub ID - fxwalsh.

| Topic                             | Direction     | Purpose                                          | Payload (JSON)                                               | QoS  | Retained? |
| --------------------------------- | ------------- | ------------------------------------------------ | ------------------------------------------------------------ | ---- | --------- |
| `/<userID>/telemetry/environment` | Publish       | Periodic + on-change **sensor telemetry**        | `{"userID":"alice","temp":22.7,"humidity":48.2,"ts":1731326400}` | 0    | ✅         |
| `/<userID>/cmd/leds`              | **Subscribe** | **Incoming LED commands**                        | `{"state":"on"}` or `{"state":"off"}`                        | 1    | ❌         |
| `/<userID>/state/leds`            | Publish       | **Current LED state** after any change           | `{"state":"on"}` or `{"state":"off"}`                        | 1    | ✅         |
| `/<userID>/status`                | Publish       | Device **presence** (`online`/`offline`) via LWT | `"online"` or `"offline"`                                    | 1    | ✅         |

**Why these choices?**

- Telemetry is frequent → **QoS 0**, **retained** so dashboards get the latest instantly.
- Commands should be delivered at least once → **QoS 1**, **not retained** (avoid replay).
- State should be discoverable by late joiners → **QoS 1**, **retained**.
- Status represents presence → **QoS 1**, **retained** (set via LWT + on connect).

> Examples below assume `USER_ID=user1`, yielding topics like `/user1/telemetry/environment`.

## 🧠 1. Background

| Feature             | Web API                        | MQTT Messaging                                |
| ------------------- | ------------------------------ | --------------------------------------------- |
| Communication Style | Request/Response               | Publish/Subscribe                             |
| Data Flow           | One-to-one                     | Many-to-many                                  |
| Connection          | Short-lived HTTP               | Persistent TCP                                |
| Typical Use         | On-demand data                 | Continuous telemetry                          |
| Example             | `PUT /api/leds {"state":"on"}` | Publish `{"state":"on"}` to `/<USER_ID>/leds` |
